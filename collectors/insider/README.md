# 내부자 거래공시 수집기

OpenDART에서 매일 내부자 지분 공시를 받아 원문을 파싱하고,
1층(노이즈 제거)·2층(방향) 규칙으로 분류해 저장합니다.
결과는 대시보드 **기업데이터 > 내부자 거래**(`dashboard/insider`)에서 봅니다.

## 매일 갱신 (GitHub Actions)

`.github/workflows/update-insider-dashboard.yml`이 평일 19:37·22:37(KST)에 돈다.

1. 최근 5일 공시를 다시 받아 `data/days/`(커밋됨)에 쌓는다. 원문 캐시는 저장하지 않는다(`--no-raw`).
2. 종가·이중분류·시총은 증시데이터가 올리는 `market-charts` 릴리스의 charts.zip(종목차트 파일)을 풀어 `--price-db`로 넘긴다.
3. `site_export.py`가 화면과 데이터를 `dashboard/insider`로 내보내고(기업 파일에서 종가 배열은 뺌), 바뀌었으면 커밋 후 사이트를 다시 배포한다.

저장소 Secrets에 `OPENDART_API_KEY`가 있어야 한다.

## 준비

```
pip install -r requirements.txt
copy .env.example .env      (Windows)  /  cp .env.example .env
```
`.env`의 `OPENDART_API_KEY=` 뒤에 발급키를 넣습니다. 환경변수로 넣어도 됩니다.

## 실행

| 명령 | 하는 일 |
|---|---|
| `python collect.py` | 최근 3일 다시 수집 + feed 갱신 (매일 돌리는 기본 명령) |
| `python collect.py --date 20261106` | 하루만 수집 |
| `python collect.py --from 20260701 --to 20261106` | 기간 백필 (이미 받은 날은 건너뜀, `--force`면 다시) |
| `python collect.py --feed-only` | 수집 없이 화면 데이터만 다시 만들기 |
| `python site_export.py ../../dashboard/insider` | 웹 대시보드로 내보내기 |
| `python -m unittest discover tests` | 실제 공시 샘플로 파서·규칙 테스트 |

옵션: `--workers 4`(원문 동시 다운로드 수), `--feed-days 120`(화면 기간), `--no-raw`(원문 캐시 저장 안 함), `--price-db`(종가 DuckDB 파일 또는 종목차트 폴더).
평일 하루치는 대상 공시 70~210건이고, 원문을 받는 데 2~4분 걸립니다. 일일 한도(2만 건)에 걸리면 저장 후 멈추고 다음 실행 때 이어서 받습니다.

## 수집 대상

| 코드 | 공시 | 공시 유형 |
|---|---|---|
| EXEC | 임원ㆍ주요주주 특정증권등 소유상황보고서 | 지분공시(D) |
| BULK_G / BULK_S | 주식등의 대량보유상황보고서 일반 / 약식 | 지분공시(D) |
| PLAN | 임원ㆍ주요주주 특정증권등 거래계획보고서 (사전공시) | 지분공시(D) |
| MAJOR | 최대주주등소유주식변동신고서 | 거래소공시(I) |

공개매수·의결권대리행사 공시는 목록만 `context`로 남겨 둡니다(4층 경고 태그용).

## 분류 규칙 (insider/classify.py)

거래 한 행마다 `event`(유형), `direction`(방향), `view`(어느 목록에 들어가는지)를 붙입니다.

**view**
- `insider` 내부자 정제 목록
- `external` 외부 5%·기관: 약식 대량보유, 보유목적이 단순·일반투자인 일반 대량보유, 금융기관·운용사·VC 이름의 주요주주, 우리사주조합
- `noise` 거래가 아닌 변동: 신규선임·신규보고·퇴임·특수관계 추가/제외, 무상증자·합병·신규상장·병합, 상속, 우리사주·상여·RSU, 대차·차입, 수량 변동 없음
- `dup` 중복·정정: 같은 사람·같은 날·같은 유형·같은 수량이 여러 보고서에 실리면 하나만 남김(임원보고 > 대량보유(일반) > 최대주주변동 > 약식 순). 목록 비고에 '정'이 붙은 정정 전 원본도 여기로.

**direction** (insider 안에서)
- `buy` 장내·장외·시간외 매수, 스톡옵션 행사, 유상증자 참여
- `gift` 증여·수증 (같은 날 같은 수량이면 상대방을 짝지어 표시)
- `sell` 매도
- `caution` 전환사채·신주인수권 등 전환·행사, 주식 외 증권 매매
- `other` 사유가 '기타'인데 비고로도 판정이 안 된 것

사유가 '기타'면 비고 문구(예: "우리사주조합계정 대체입고", "퇴임으로 특수관계인 제외")로 다시 판정합니다.

## 저장 구조

```
data/days/YYYY/YYYYMMDD.json.gz 하루치 전체(보고서 메타, 거래 행, 거래계획, 오류)
data/raw/                       공시 원문 캐시(규칙을 바꿔 재분류할 때 사용)
viewer/data/main.js             내부자 매매(하루·사람·유형 묶음)·증여·거래계획·종목 정보
viewer/data/bulk.js             외부 5% 대량보유(보고서 단위)
viewer/cdata/<코드>.js          기업 페이지: 종가 + 그 종목 내부자 공시 낱개 + 지분율 보고
```

화면: `viewer/trades.html`(내부자 매매), `gifts.html`(증여), `bulk.html`(대량보유), `company.html?code=종목코드`(기업 페이지).
수집이 끝나면 `collect.py`가 위 화면 파일을 자동으로 다시 만든다. 로그 끝의 '점검 필요' 목록은
최근 7일 중 '기타'·'사채·증자'로 빠진 내부자 행이다(분류 규칙 점검용).

## 알려진 한계

- 오늘 올라온 공시 중 일부는 DART 원문이 늦게 올라와(오류 코드 014) 그날은 빠질 수 있다. 다음 실행이 최근 5일을 다시 받으므로 채워진다.
- 정정 처리는 목록 비고 '정'에 기대므로, 오래전 보고서가 한참 뒤 정정되면 원본이 남을 수 있다.
- 종목차트 종가는 수정주가라, 액면분할 등이 있었던 종목은 과거 거래 금액 추정이 실제와 다를 수 있다.
